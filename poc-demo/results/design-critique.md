# BNaaS design critique and question bank (2026-09-09, draft 2, code-verified)

> The previous model, measured 2026-09-09 and 2026-09-10: a destination-keyed
> delivery topic, a populator switch and a barrier cutover. On 2026-09-11 the
> workers moved to today's topic and every change became a seeded container
> swap; the measurements of that model are in `poc-demo/PLAYBOOK.md`. Kept
> here because the findings that do not depend on the topic still stand.

Scope: Citadel PR scality/citadel#383 at 68daf530 (Taylor's 2026-09-07 restructure of Anurag's July design), read against the product requirements in PR #373, the Citadel standards folder at b233fd1, the July scale test, and the August/September POC on `poc/S3C-11127-workgroups`. Code facts below were verified line by line on backbeat `development/9.3` @ dd3cb0d4, CloudServer `development/9.3` @ 4628dd2ad (Arsenal 8.4.11 installed), node-rdkafka 2.18.0 / librdkafka 2.3.0. Full verification reports: `scratchpad/verify-backbeat-legacy.md`, `verify-cloudserver-api.md`, `survey-kerberos-e2e.md`, `survey-poc-vs-design.md` (copied to `gw2cto/reports/`).

## 0. The things to fix before the CTO reads anything

1. **The document says "Go worker" where it means the Node queue processor handling multiple destinations (a carry-over from the June version, wording only).** Reading rule: the doc's two resolution strategies already exist as Node code, pooled = the POC `DeliveryWorker`, single-destination = today's `QueueProcessor`; generation v0 in §16 is today's processes. Still, the text as written contradicts the record: PR 383 says "one unified Bucket Notification Queue Processor V2 (Go)" in the Overview, §1, §7, §13 (cgo crash class, goroutines), §14 (confluent-kafka-go checklist) and §17 rejects "Pure-Node pooling (extend Backbeat in place)". Anurag's Jira comment on S3C-11127 (2026-07-24) records the engineering-management constraint "use Backbeat only"; the 2026-08-05 leads report recommends the Node pool; the 16.7k-line POC is Node. François Ferrand's PR 364 review asked exactly "why rewrite in Go instead of extending backbeat". If the CTO doc says Node and the linked design says Go, the meeting is about that and nothing else.
2. **Two different "workgroups" exist and the document describes the one that was not built.** PR 383 §7a: one topic per workgroup, the populator routes each event to one topic, ZooKeeper generation plus `apply_after` plus a per-worker barrier that prevents overlap. POC: one shared delivery topic keyed by destination, each workgroup's consumer group reads the whole topic and skips records outside its slice (`utils/workgroups.js:289-312`, `DeliveryWorker.js:173-178`), a Kafka barrier record plus a ZooKeeper document as the commit point, a cutover CLI with a drain report that permits overlap and pays duplicates to guarantee no gap. PR 383 D17 explicitly rejects the shape the POC built ("read the shared topic and discard"). The POC shape has five green gates and measured numbers; the document shape has none. The rejection is a cost argument (G-fold reads), not a correctness one; present it as a trade.
3. **FR10 (one event, one notification, first-match-wins across destinations) is a silent customer-visible behavior change that the POC does not need.** FR10 exists because per-workgroup topics turn multi-destination fan-out into a multi-topic publish. With one delivery topic, fan-out is N keyed records in one batch, the same atomicity as today, and the POC does exactly that (`NotificationQueuePopulator.js:289` loop, `:323` publish). Verified today's behavior: the populator already does full per-rule matching per destination (`_processObjectEntry`, `:255-304`), so keeping fan-out costs nothing new. Measured (M8): a catch-all rule to destination 1 plus a `logs/` prefix rule to destination 2 delivers `logs/x` to both destinations on the legacy path and on the pool path; FR10 as written would deliver to destination 1 only. Recommendation: drop FR10 and D14, keep today's fan-out, remove §16's overlap scan. The requirements say "same rule structure" and "no events missed"; a rule that silently stops delivering to a second destination violates both.
4. **The reliability posture contradicts the product requirements.** PR 373: "at-least-once, best-effort", "failures are retried and abandoned once the retry strategy is exhausted", drops logged with cause. PR 383: Posture A, drop on first failure, retries "designed for, not built". Today's real behavior (verified): the destination swallows the producer error and calls back clean (`KafkaNotificationDestination.js:118`), the consumer commits even on task error (`BackbeatConsumer.js:578`), `message.timeout.ms` is never set so librdkafka retries silently for 5 minutes, and the failure branch records no counter or histogram sample (null delay). So "today" already is "retry ~5 min, then silent drop". The design should name a configurable bounded retry window (the POC's `deliveryTimeoutMs`, 30 s default, 6 s to 240 s) as the GA behavior in the requirements' words.
5. **Validation semantics contradict the product requirements.** PR 373: test on create and update, no user-facing test API. PR 383 §6.1: create-time validation OFF by default, `Validate=true`, a standalone `TestBucketNotificationDestination` action, `SkipDestinationValidation` and `RevalidateAll`. Decide with product before the review; the infrastructure-as-code argument for a skip flag is good and should be made to David Tencer explicitly.
6. **Account-scoped ARNs collide with global destination names on every legacy component (new, from code).** Backbeat matches an ARN by its last colon segment only (`NotificationQueuePopulator.js:265`, `QueueProcessor.js:256`; `constants.arn` is defined and never used). CloudServer compares only `queueArn.split(':')[5]` against the static list (`getNotificationConfiguration.js:16-17`), and Arsenal's parser accepts any 6-part ARN with the prefix (`NotificationConfiguration.ts:300-314`). So `arn:scality:bucketnotif::123456789012:target1` is accepted by an old CloudServer, and an old populator or processor delivers account 123456789012's events to the global destination `target1`. Silent cross-tenant misrouting during any mixed-version or downgrade window. Fix options: forbid account-scoped names that equal a global destination name (cheap, but a global destination created later still collides), or make the account-scoped name segment structurally distinct (e.g. `<accountId>/<name>` as the last segment), or patch legacy components to require an empty account field. Must be decided in the design.
7. **`schemaVersion` is already taken.** The internal message carries `schemaVersion` today, populated from `md-model-version` (`utils/message.js:13-24`), never read. The design's "bumped schemaVersion" would collide with a live field; pick another name.

Smaller but certain to be raised: the ARN in §6.1 and §8 has five fields; the six-field form `arn:scality:bucketnotif::<accountId>:<name>` matches the live Scality convention for utapi, metadata and sur (`RequestContext.ts:111-138`) and passes today's parser, the five-field form fails with `MalformedXML`. The PR is a draft with no reviewers requested. The doc has no measured numbers while a full scale test and five POC gates exist.

## 2. Code facts that change sentences in the design

- **The populator is not a singleton (§2, §12, Risks).** On S3C (`logSource: bucketd`) every populator process registers as leader candidate and owner (`ProvisionDispatcher.js:84-86`); the leader only round-robins raft sessions to owners (`:156-213`); each owner builds one `RaftLogReader` per assigned session (`QueuePopulator.js:388-399`) and runs them in parallel (`:540`). R raft sessions give R concurrent tail loops across N processes. The "largest unquantified risk" is misframed; rule matching already runs per destination today (Q1), so routing adds a key computation, not a matcher.
- **A latent populator hazard the redesign touches.** Readers in one process share the extension instance; the publish batch is swapped per reader around its filter phase (`LogReader.js:59-65, 582-584`) and the contract is that `publish()` runs synchronously inside `filter()` (assert at `QueuePopulatorExtension.js:78`). The notification extension awaits the config fetch before publishing, so with two readers in one process a message can land in the other reader's batch or hit the assert, which exits the process (`bin/queuePopulator.js:42`). Reachable when a process holds two or more raft sessions; on S3C the container count is at least the raft-session count by construction, so this needs several populator containers down. Worth a line and a unit test, not a headline.
- **Unknown ARNs are safe on downgrade; malformed shapes are not.** Unknown ARN: skipped, no log, no metric (`NotificationQueuePopulator.js:264-271`). Malformed `queueConfig` or non-string `queueArn`: throw, batch fails, offset unsaved, `process.exit(1)`, crash loop (`bin/queuePopulator.js:36-42`). On S3C the notification populator is its own container so replication and lifecycle are unaffected; on Zenko one populator carries every extension. The design's VERIFY 3 is answered: keep the stored shape, add fields only.
- **Legacy processor tolerates extra fields (VERIFY 2 answered) but the field name `schemaVersion` is occupied.**
- **CloudServer today makes no outbound call on the notification path.** No Kafka client anywhere (`package.json`, `lib/`), PUT parses XML, checks the name, writes bucket metadata (`bucketPutNotification.js:30-43`). The design's synchronous test dial (F2, ~10 s per destination, parallel) puts an operator-supplied endpoint on the S3 request path. CTO question: latency, timeouts, and what a slow customer broker does to the S3 worker pool.
- **Service-root query actions have no precedent.** `routeGET.ts:28-32` has one handler at `/` and ignores the query string, so `GET /?notification-destinations` on an un-upgraded node returns ListAllMyBuckets, and an unknown `POST /` returns NotImplemented with HTTP 200 (`routePOST.ts:68-69`). The design's "bucket-policies pattern" is bucket-scoped; account-scoped routes need Arsenal route changes. The `/_/` internal routes (`routes.ts:248-261`) with SigV4 plus Vault policy evaluation are the real precedent; `routeMetadata.js` is the template, and the "any authenticated user can access API" shortcut in `routeBackbeat.js:1666` must not be copied.
- **Credential encryption precedent exists and is RSA.** `decryptSecret` (RSA-OAEP/SHA-256, node-forge) protects external-backend credentials in Arsenal `locationConstraints.ts:97,135,159`, under the Zenko management overlay only. `lib/kms` is object SSE (AES-256-CTR, pbkdf2 with a hardcoded salt). The design's AES-256-GCM envelope is new; say why it is preferred over the existing RSA path (DRY clause).
- **Delivery failures are invisible today, and the processor's metrics route is not wired on S3C** (BB-625 TODO at `NotificationConfigValidator.js:93-95`). External producer `acks=1`. Partition assignment eager and unconfigured.
- **A confirmed consumer misconfiguration since 2023 (`reports/verify-metadata-maxage.md`).** `BackbeatConsumer.js:235` sets `metadata.max.age.ms: 5000` (commit a9208f56, BB-454, 2023-10-17, present on every 9.x line) but never sets `topic.metadata.refresh.interval.ms`, which librdkafka leaves at 300000; librdkafka derives max age as 3x the refresh interval only when it is not set explicitly (`rdkafka_conf.c:454-457, 3930-3933`), and no warning covers the pair. Expiry triggers a topic-only refresh with `cgrp_update = false` (`rdkafka_topic.c:1719`, `rdkafka_metadata.c:977`), so the consumer group's view of the topic flips to unknown and a join that lands on an expired entry falls into an unconditional eager revoke with the reason "Metadata for subscribed topic(s) has changed" (`rdkafka_cgrp.c:5455-5462, 5512-5514`), rejoining every 1 to 2 s (`:5178`). No dependency on broker count, leader placement or broker version; only on the eager protocol, which is backbeat's default. Reproduced deterministically on the rig (50+ assign/revoke cycles per minute, nothing fetched); fixed there by injecting a 2000 ms refresh interval. Same engine as the design/06 wedge trigger, different entry point (design/06's is a real broker `UNKNOWN_TOPIC_OR_PART`, negative-cached 100 ms); the fix removes this trigger and shrinks that one, and does not fix the lost-callback wedge itself. Recommended BB ticket: replace the 5000 override with `topic.metadata.refresh.interval.ms: 2000` (max age derives to 6000), which also serves BB-454's original goal better since partition-count changes only reach the group on a `cgrp_update = true` response. Production prevalence is unmeasured; the rig shows the mechanism, not the field frequency.
- **Kerberos, GATE 2 answered empirically (`krb-spike/RESULTS.md`, 33 raw evidence files).** Rig: MIT KDC, Kafka 3.4.0 with SASL_GSSAPI and ACLs binding each principal to one topic (so a collision is a binary `Topic authorization failed`, not a log-reading exercise), two producers in one Node process on `backbeat:bb828-gssapi` (node-rdkafka 2.18.0, librdkafka 2.3.0), 9 rounds across 4+ ticket refreshes. Baseline (backbeat's exact `kinit -k <p> -t <kt>`, `utils/auth.js:83`): the broker authenticated both connections as the last principal that ran kinit; the other producer delivered 0 of 9 with `Topic authorization failed`. The design's `DIR:` workaround as written does not run (`kinit: Subsidiary cache path ... does not begin with "tkt"`); with legal names both tickets coexist but the identity is chosen by cache filename, never by producer (renaming the caches flips the winner). `sasl.username` has no effect. `DIR:` plus `kswitch` passes for 45 s and fails on the first broker restart (producer a never authenticates again over 4 restarts). Two OS processes, one principal each, pass 9/9 and 9/9. Root cause in source: librdkafka runs `kinit` as a bare `system()` under a process-global mutex (`rdkafka_sasl_cyrus.c:49-63, 228-232`), never sets `KRB5CCNAME`, and passes no client identity to GSSAPI (`:547-551`). Trap for anyone diagnosing this: librdkafka's client-side `Authenticated as <principal>` line echoes the configured principal, not the credential used; only the broker's `authenticationID=` line is evidence. Conclusion for the design: one OS process = one Kerberos identity with librdkafka. **The per-connection alternative is proven (2026-09-10, `krb-spike/pure-js/RESULTS-nodejs.md`):** KafkaJS 2.2.4 with a ~90-line custom GSSAPI SASL mechanism over the npm `kerberos` binding (2.2.2 tested, 7.0.0 identical), which calls `gss_acquire_cred` with a desired name per client (`kerberos_gss.cc:249-256`) where librdkafka passes `GSS_C_NO_CREDENTIAL`. Same rig, same ACLs: `DIR:` collection 9/9 and 9/9 (the layout that failed under librdkafka), client keytab with no `kinit` at all 9/9 and 9/9, control without a desired name collides, three broker restarts 24/24 and 24/24 with both principals in every epoch (what killed librdkafka's `kswitch` arm), 2-minute tickets over 300 s with independent reacquisition 25/25 and 25/25, and 50 distinct principals from one process 250/250. Footprint: 82 MB RSS and 11 threads at 50 identities (KafkaJS is pure JS, no native producer threads). **Landed inside backbeat** on `poc/S3C-11127-kerberos-producer` (origin, da7b7519, nine commits on top of the workgroups POC): `KerberosKafkaProducer.js` on the `BackbeatProducer` surface, `saslGssapi.js` (RFC 4752 state machine, binding injected so it unit-tests without the native module), `kerberosCredentials.js` (`DIR:` collection or a JS keytab merge for client-keytab initiation, no `kinit`, no `ktutil`), `deliveryProducerFactory.js` selecting the stack per destination, `deliveryPool.kerberosProducer` and `auth.credentialSource` config keys defaulting to today's behaviour, `libkrb5-dev` in the Dockerfile builder stage, 5 unit suites and a functional suite (`ft_test:notification:kerberos`, README) driving `DeliveryProducerPool` in one process: arms A, B, D, E, F, G pass, C (rdkafka control) collides; 1720 unit tests green, lint clean. Footprint through the pool: 140 to 146 MB RSS and 11 threads for 50 kerberised producers. Known limit: KafkaJS cannot produce zstd, so such a destination is refused at construction. Not proven: Active Directory, cross-realm, SASL_SSL, channel bindings, throughput, `connections.max.reauth.ms`, scale beyond 50. Maintenance fact to state: KafkaJS ships no GSSAPI mechanism and last published 2023-02, so the team owns the mechanism; the `kerberos` package is Apache-2.0 and actively released. Gotcha for the code: a KafkaJS custom mechanism must hand back an already length-prefixed BYTES buffer.
- **FR8.1 "bug-for-bug" would freeze a real bug.** `_getEventDateTime` returns null `eventTime` whenever `overheadFields` is present without a timestamp (measured matrix in `design/07`). Decide: reproduce or fix, explicitly.
- **`_deleteRequiresOplogUpdate` keys off `getNotificationConfiguration()`** (`deleteObject.js:7-18`). The bucket-level configuration stays on `BucketInfo` in this design, so nothing breaks, but any future move of that state off `BucketInfo` silently stops forcing oplog entries on delete.

## 3. Question bank: what the CTO and the leads will ask, and what we answer

Status: P proven on rig or lab, R to run this round, D design-only, U unknown.

### Migration and rollback
- Rollback if a bug is found mid-migration? Two paths. Drainer path (measured, M4): legacy processors resume from their untouched offsets and re-deliver exactly the drained records (106 duplicates), and whatever the pool had not committed when it died is stranded on the delivery topic (161 records, 21% of the rollback window); the arithmetic closes exactly, and a later roll-forward recovers the stranded records but out of order (3190 same-key inversions on the 3 straddling keys). There is no reverse drainer; write one before the first customer cutover. Drain-then-switch path (the doc's §16, measured M2b/M4b): cutover 0 of 601 lost, 69 avoidable duplicates, rollback 0/0/0. P. Recommendation: drain-then-switch is the default; keep the drainer for a legacy processor that cannot drain.
- When is the migration done? When every legacy group is at lag 0 (drain-then-switch) or the drain report reaches zero (drainer) and the legacy programs are removed. P: M2 cutover with a 10-record parked backlog under 2 ops/s load for 9 minutes, 1168 of 1168 delivered, 0 gaps, 0 duplicates, 0 inversions, legacy offsets untouched.
- Operator stops the old processors too early? Loss of exactly the un-drained records; the tool warns first. P (E2).
- Both old and new running? Nothing lost and, contrary to what we assumed, nothing doubled: the populator publishes each event to exactly one topic (an if/else on the flag), so a legacy processor and a pool worker running together partition the stream (M5: 350 + 307 = 657 of 657, 0 duplicates). Duplicates in a migration come only from the drainer. P.
- A crashed old-generation worker mid-drain? Cannot resume; amendment proposed. P (E4). Say it first.
- Downgrade with account-scoped ARNs in bucket metadata? Measured (M6, M7). Unknown ARN: today's CloudServer refuses the PUT (400 InvalidArgument, name not in the static list), but a stored one is served verbatim on GET and skipped silently by the populator with no log and no metric. Name collision: `arn:scality:bucketnotif::123456789012:poc-dest-1` is accepted with HTTP 200 and all 12 events were delivered to the global `poc-dest-1`, through the supported API, no new code. Shape: a `queueConfig` entry without `queueArn` bricks the bucket at the S3 API (500 on PutObject, GetObject and PutBucketNotificationConfiguration itself, repairable only by a direct metadata write) and crash-loops the populator with its offset frozen, stalling every tenant's notifications until the metadata is repaired (nothing lost, unbounded stall). Legacy processor on addressed records: 24 of 24 delivered, no crash, byte-identical event shape; but it re-matches by its own destination id (fan-out, not routing) and re-delivers everything on roll-forward unless the pool group is advanced first.

### Delivery semantics
- At-least-once or at-most-once? Consume is at-least-once. Delivery today when a destination is dead (M10, measured): a per-destination processor cannot start at all if the destination is down at start (`Client is disconnected`, exit, crash loop); one already running attempts only `concurrency` records, waits the 300 s librdkafka `message.timeout.ms` default, then fails its commit with `Group partition assignment lost` because 300 s exceeds `max.poll.interval.ms` (the BB-787 self-eviction chain), never advances any offset, writes nothing to the configured failed topic (no code reads it), exposes no counter, and stays up. So today is a silent stall, not a silent drop. The pool worker started with four dead destinations, dropped 60 of 60 with `dropped_total{target,reason}` exact per destination in ~30 s (`deliveryTimeoutMs`) or instantly on connect refusal, committed past them, and delivered 5 of 5 to a healthy destination at the same time. Requirements' "retry then abandon, logged" is exactly the pool's behavior; name the window in those words.
- Duplicates? Bounded and explained, all measured. Populator `kill -9`: 0 duplicates across two kills and 658 events, because a batch is produced in one send and only then checkpointed; the real window is between the Kafka ack and the ZooKeeper write and replays the whole batch (up to `batchMaxRead`, 10000), low probability, high amplitude (M11). Worker `kill -9`: 89 duplicates from a 125-record uncommitted window, 0 gaps (M12); the bound is the consumer's 5 s auto-commit interval times the delivery rate, not `concurrency`, and that interval is not exposed in the `deliveryPool` schema. Workgroup cutover: the old generation's post-barrier consumption, 18 to 30 per ~100, operator-time bound (W-C, E1). Consumers de-duplicate, as the requirements state; `s3.object.sequencer` is the right key and is null today.
- Ordering? Per bucket/key within a destination by construction; 0 inversions across the M2 cutover (785 keys, 3 straddling every boundary), across two populator kills and a worker kill, across M2b and M4b, and across a reshard. Two ways to lose it, both measured: starting the pool before the legacy processor has drained (M2c, 284 inversions on 3 keys, the reorder the design's barrier exists to prevent), and a rollback followed by a roll-forward of stranded records (M5, 3190 on 3 keys). One qualification, now evidence-backed: a single same-key inversion was delivered by the legacy processor before any migration step (M2b, 1 in ~1200 legacy-delivered events; 0 in the pool's several thousand). Ruled out: checker artefact (driver, sizes and record key check out), populator (internal topic partition 3, offsets 346 Put then 347 Delete, same key), producer reorder (the processor logged the Delete's send 5 ms before the Put's, and the customer offsets follow that order), and the scheduler (`BackbeatConsumer` defaults `orderByFunc` to the message key and `send` resolves only on the delivery report). What remains: the two entries reached the scheduler out of order, in the processor's first consume burst after assignment, i.e. under the same rebalance-racing-the-pipeline conditions as the wedge; the main consume loop is guarded against concurrent calls (`BackbeatConsumer.js:425-434`), so the exact path is unconfirmed and needs a debug-level reproduction. It is a `BackbeatConsumer` property, so it applies to the pool worker too. Until reproduced, neither path should claim per-key ordering without this qualification, and the requirements should state it as the target, not as an existing guarantee. Not in the requirements: get it written in.
- One slow or dead destination? Its own lane, its own offsets, neighbours unaffected (W-B; M10: 5 of 5 to the healthy destination while 60 were being dropped). Caveat: the pre-existing consumer wedge fired on 4 of 16 consumer starts in this round (two worker starts, two legacy processor starts), with the metadata-refresh shim active, so the refresh fix is not sufficient; a wedged member holds its partitions, answers the liveness probe, delivers nothing, and a restart costs up to 40 s waiting for its session to expire. Every runbook step needs an "is it actually delivering" check.
- Detach vs delete? Measured (M9): legacy dropped 20 of 20 queued events after a detach, silently (nothing above debug, no metric); the pool delivered 20 of 20. Release-note material in both directions; product acknowledgement needed.

### Scale
- New bottleneck? Producer connections per worker, then partitions. Memory is no longer the wall (0.75 MB vs 936 MB per destination). P (July).
- Populator cost? Matching already runs per destination today (Q1); routing adds a key. Tail loops are per raft session, not a singleton (Q9). D, code-verified. Also measured: one destination occupies exactly one delivery partition when `spreadFactor` is 1 (all 1168 M2 records on partition 2 of 3), so single-destination parallelism is one worker regardless of pool size; capacity for a hot destination goes through `spreadFactor` with the guaranteed-m table.
- Why not a topic per destination? 30,000 partition replicas on 6 brokers shared with CRR and lifecycle; ceiling 1,000 to 2,000. D.
- Adding a node adds capacity? ~500 to 600 fully distinct destinations per node (estimate from measured constants); density gate on a lab outstanding.
- 80,000 buckets? Bucket-config cache is the one bucket-scaling item; unmeasured. U.

### Isolation, faults, security
- Worker crash blast radius? All destinations on that worker until restart; workgroups bound it. P for reassignment, D for OOM cause.
- Hostile customer broker? Same C library as today; radius widens from one destination to one worker; pin to a one-destination workgroup. D.
- SSRF via the test dial? Dial-time validation against the deployment's own addresses. D; requirements do not address it yet.
- Secrets? AES-256-GCM envelope, key on CloudServer only, write-only API; first platform key rotation, a risk to name. D.
- Cross-tenant misrouting by name collision? 0.6; must be closed in the design.

### Kerberos
- Two principals in one process? Not with node-rdkafka (measured: the losing producer gets `Topic authorization failed` 9/9; `DIR:`, `sasl.username` and `kswitch` do not fix it). Yes with KafkaJS plus the `kerberos` binding (measured: 2 and 50 principals, broker restarts, ticket expiry, 82 MB at 50). P (GATE 2 closed both ways). v1 can pool Kerberos destinations on the KafkaJS producer behind the destination seam, or pin them per process; the requirements descope Kerberos for account-scoped destinations anyway. Kerberos is broken in the shipped image today (BB-828 fixes it).

### Observability and operations
- Metrics from day 1? Today none are scraped on S3C. New: delivered, dropped by reason, delay histogram, `workgroup` label, per-group lag. P on the rig. Dashboards, alerts, L1/L2 lifelines: not designed. Gap.
- The consumer wedge? Two pre-existing `BackbeatConsumer` defects, now both understood. Trigger: a 2023 misconfiguration (`metadata.max.age.ms: 5000` without a matching refresh interval) makes a join that lands on an expired topic entry rebalance every 1 to 2 s; one-line fix. Wedge: a rebalance racing an in-flight poll pins the pipeline counter, the consumer goes deaf while `isReady()` stays true, `close()` hangs, the replacement waits ~5 min for broker eviction; fix shape known. ### Alternatives
- Go rewrite: rejected 2026-07-24; two engines forever, a proven consumer to reproduce, the wall is not the runtime.
- Shared stream with in-memory dispatch: every worker may need every destination; adding workers makes it worse.
- Own assignment map: 12x to 40x read tax and three silent-loss sequences in a hand-written protocol.
- Per-destination topics: broker arithmetic.
- Fixed shards with a move protocol: five defects, buffer as prerequisite; its escape hatch survives.
- Scale by remote cluster (François): absorbed as producer pooling per endpoint and credential.

The two migration paths side by side (`rig/RESULTS.md`, "The two migration paths"): drain-then-switch needs 5 operator steps and no tooling against 7 steps plus the replay CLI and a throwaway group; populator downtime is one restart against one restart plus the drain; both lose nothing on cutover; rollback costs 0/0 against 161 stranded plus 106 re-delivered; the case drain-then-switch cannot handle is a legacy processor that never reaches lag 0 (wedged, crash-looping, or its destination dead, which M10 showed stops it from even starting), and that is exactly when the drainer earns its place. Two conditions make drain-then-switch safe and both are cheap: start the worker before switching the populator (removes the 69 duplicates), and gate the "legacy drained" step on the legacy delivery counter moving, not on lag alone (a wedged consumer's lag simply stops falling while its liveness probe answers 200; the wedge hit exactly that step in M4b, 5 of 21 consumer starts this round).

Findings to carry into the design and the CTO doc, beyond the rows above:
- No reverse drainer exists; M4's 161 stranded records are the case it covers, and the trigger is one `kill -9` of the last worker during a rollback. Write it before the first customer cutover, or use the drain-then-switch path whose rollback is symmetric.
- Adding a destination today needs both static lists (CloudServer and backbeat) edited and both services restarted, and restart order matters: a running populator that does not know a destination CloudServer already accepts skips its events silently with its offset advancing and no log line (21 objects lost this way in M10's setup). The self-service control plane removes this class.
- `delivery_timeout` is dead code in the POC worker: the delivery-report error carries `code: -1`, not `ERR__MSG_TIMED_OUT` (-192), so a real timeout is counted as `delivery_error`. Fix before the label is promised to operators.
- The pool's duplicate window is not bounded by `concurrency` nor, as first stated, by the 5 s auto-commit interval: a worker whose commit path has thrown keeps delivering with frozen offsets, so the next kill replays everything since its last good commit (C4: 1100 of 3290). Consumers must be idempotent; the interval should still be exposed.
- CloudServer's filter rule names are case-sensitive at the API (`prefix` refused) while the matcher compares case-insensitively; harmless today, worth a line in the API section.
- The `BackbeatConsumer` wedge fired on 4 of 16 consumer starts with the refresh-interval shim active: the refresh fix removes one trigger, the lost-callback wedge stands, and a wedged member passes the liveness probe.

Crash attribution (`evidence/<Cx>/exits-per-rebalance.json`): every one of the 18 crashes followed that worker's own revoke or assign; C1 one kill, two survivors dead 42 s and 49 s later; C2 three worker additions and no kills, four crashes; C3a one partition alter, three crashes, one per worker; C3b zero; C4 six. In C2 a partition was served by nobody for 199.6 s while a live worker held nothing, matching the 211 s pause the checker measured. Operational conclusions from the chaos round (`rig/RESULTS.md`, "What this means for operations"): plan rebalance pauses in minutes, not the 45 s session timeout, because every eager revoke can crash a survivor on the unguarded `offsetsStore` (`BackbeatConsumer.js:851`) and restart the cycle; alert on a destination's delivery rate, never on group membership or `/_/live`; fix the throw first, then switch `partition.assignment.strategy` to cooperative-sticky in one step (it cannot mix with eager members); grow partitions only with the populator stopped and the pool at lag 0 (0/0/0) and never for capacity (a destination stays on one partition unless spread); size the pool at one worker per partition and alert on a worker with no partitions; give `BackbeatProducer` a `topic.metadata.refresh.interval.ms` so a partition change is seen in seconds, not 257 s.
